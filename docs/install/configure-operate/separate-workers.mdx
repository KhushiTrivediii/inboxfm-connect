---
title: 'Separate Workers'
description: 'What AP_CONTAINER_TYPE actually switches in the unified image'
icon: 'robot'
---

The unified image runs as app, worker, or both, switched entirely by the
`AP_CONTAINER_TYPE` environment variable (`APP`, `WORKER`, or `WORKER_AND_APP`,
the default) — see the [production checklist](/install/configure-operate/production-checklist).
There is no separate worker package or image in this repository.

<Warning>
In the current codebase, a `WORKER` container does not take execution work off
the app container. The worker-mode process registers only the health module —
`packages/server/api/src/app/server.ts` gates every app module on
`system.isApp()` — while integration execution and the system-job scheduler run
inside the `APP` process. Scaling `AP_CONTAINER_TYPE=WORKER` replicas therefore
does not add execution capacity; run and scale the default `WORKER_AND_APP`
container instead.
</Warning>

Older, inherited versions of this page described a queue-based worker
deployment: a `npm run workers token` CLI command minting an
`AP_WORKER_TOKEN`, workers pulling jobs from the app's queues, and an
"Infra → Workers" page in the admin console. None of that exists in this fork:

- No code reads `AP_WORKER_TOKEN` — nothing in this fork ever did. The
  vestigial `workers token` CLI command and the entrypoint auto-mint that
  produced it have been removed.
- There is no queue-consuming worker process — the `packages/server/worker`
  package was removed from the tree, and with it the job-pulling loop this
  page used to configure.
- The web console has no workers infrastructure page.

If an older guide directed you here, `AP_CONTAINER_TYPE` is the only
worker-related switch that exists in this codebase.
